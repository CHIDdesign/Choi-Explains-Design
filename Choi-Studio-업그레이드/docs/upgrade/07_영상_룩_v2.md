## 0. 결론

1. **이번 영상의 색 문제는 대부분 버그 하나다.** 설치본의 `skin_guard`(수정 전)는 CIELAB 색상 12~100° 를 전부 피부로 보고 32~60° 로 끌어당긴다. 누런 벽(색상 약 89°)이 그 경계에 걸려 1번 카메라에서는 **얼룩**이, 2번 카메라에서는 벽 전체가 **분홍·주황**이 됐다. HEAD `ce2f323` 의 `grade()` 를 같은 원본에 돌리면 둘 다 사라진다. → 설치본 갱신이 P0 이고, 진단 6절의 "따뜻한 방 + 웜 룩이라 주황 한 덩어리"는 **원인 진단을 고쳐야 한다**(룩이 더한 온기는 b* +0.0 이었다).
2. **HEAD 에도 남는 것이 셋 있다.** 이미 자연스러운 얼굴(색상 38°)을 50° 선으로 더 돌려서 벽이 초록으로 간다. 노출 감마를 채널별로 걸어 채도가 덩달아 오른다(벽 채도 23 → 27.5). 화면 속 전등 때문에 화이트 포인트를 당겨 전등·침구가 날아간다(클리핑 0.2% → 1.7~2.0%).
3. **두 원본을 한 톤으로 묶는 단계가 없다.** 컬러리스트는 1번 카메라 시트만 보고 룩을 정하고, 2번은 그 룩을 물려받는다. 교정이 따로 돌아 얼굴 ΔE 가 4.4~5.0 남는다. 얼굴 기준 Lab 이동 한 번으로 1.8 까지 줄어든다(시제품 실측).
4. **완성본이 풀레인지 BT.601 로 나갔다**(`yuvj420p` · `pc` · `bt470bg`). `render.mjs` 에 `colorSpace: 'bt709'` 한 줄이 빠졌다.
5. 마감(입자·할레이션·비네트)은 그 다음이고, **기본은 "덜 하기"** 다. 깨끗한 아이폰 영상에 시간축 디노이즈와 샤픈이 항상 걸리고 있다.

### 1-4. 그 밖에 확인한 것

- **완성본 태그**(`ffprobe`): H.264 Main · `yuvj420p` · `color_range=pc` · `color_space=bt470bg` · `color_transfer=unknown` · `color_primaries=unknown` · 1920×1080 · 30fps · 영상 15.68 Mbps · AAC 283 kbps. x264 서명이 없어 Remotion 의 `h264_nvenc` 로 본다(추정). 프록시 두 개는 `yuv420p` · `tv` · `bt709` 로 정상.
- **원본**: iPhone 14 Pro, 1080p H.264 8비트 BT.709, 약 15 Mbps. 프록시도 1080p 라 재프레이밍 여유가 없다.
- **NVENC**: 번들 FFmpeg n9.0.2 는 드라이버 610.00 이상을 요구하는데 이 PC 는 그보다 낮다. `h264_nvenc` 가 열리지 않아 프록시가 x264 로 갔다(566초). 조용히 떨어져서 로그에 이유가 없다.
- **정리 필터**: 두 카메라 모두 `noise` 0.0087 / 0.0056 인데 `hqdn3d=1:1:3:3` + `unsharp=5:5:0.35` 가 걸렸다. 가장 약한 등급이 "없음"이 아니다.

### 2-2. 피부 밴드 — 이미 자연스러운 얼굴은 돌리지 않는다

`_skin_line_gains` 는 얼굴 색상을 늘 50° 로 보낸다. 얼굴이 이미 편안한 대역 안이면 화이트밸런스를 피부 때문에 더 돌리지 않고, 밖이면 **가까운 경계까지만** 보낸다(`skin_fix` 가 마지막 단계에서 쓰는 것과 같은 생각).

```python
SKIN_BAND = (36.0, 56.0)      # 제안. 자연 범위 32~60° 에서 양쪽 4° 안쪽

def _skin_line_gains(face_rgb, gains, band=SKIN_BAND, steps=12):
    h = _face_hue_after(face_rgb, gains)          # 지금 게인을 건 뒤의 얼굴 색상
    if band[0] <= h <= band[1]:
        return np.array(gains, np.float64)        # 그대로
    return _solve_to_hue(face_rgb, gains, target=band[0] if h < band[0] else band[1], steps=steps)
```

시제품 실측(1번 카메라): 게인 (0.926, 1.024, 0.983) → (0.977, 1.003, 1.039). 벽 색상 96° → 90°(원본 89°), 얼굴 색상 37°(원본 38°).

### 2-4. 따뜻한 방 규칙 — 룩 선택과 상한이 장면 온기를 따른다

온기를 **더하지 않는** 규칙은 이미 있다(`plan_recipe` 의 `mid_b` 감쇠). 빠진 것은 ① 룩 자체를 바꾸는 것 ② 이미 진한 배경을 **내리는** 것 ③ 컬러리스트에게 장면 온기를 숫자로 알려 주는 것이다.

`measure()` 가 내는 값에 벽 통계를 더한다(얼굴 상자 기둥을 뺀 밝은 배경 — 1-2 에서 쓴 영역). 문턱은 제안이다.

| 장면 | 조건(교정 뒤) | 기본 룩 | 세기 | 온기 상한(b\*) | 배경 채도 이득 범위 | 컬러리스트 `warmth` |
|---|---|---|---|---|---|---|
| 차갑거나 중립 | `wall_b < 8` | `warm_rich` | 0.8~1.0 | +9(지금 값) | 1.0~1.8 | −0.1~+0.2 |
| 조금 따뜻함 | `8 ≤ wall_b ≤ 16` | `warm_rich` | 0.7~0.9 | +4 | 1.0~1.4 | ≤ +0.1 |

### 2-5. 화면 속 전등(프랙티컬)

전등이 화면에 있으면 세 가지가 틀어진다: 화이트 포인트(99.7% 지점이 전등), 무채색 후보(전등갓의 크림색이 "흰색"으로 잡힘), 피부 한쪽 뺨의 채도.

```python
def has_practical(frames, faces) -> bool:
    """얼굴 상자 밖에서 휘도 ≥ 0.92 인 연결 영역이 화면의 0.4% 이상(제안)."""

# correction_from_stats
white = max(0.8, min(1.0, st["p997"] + 0.015))
if st.get("practical") or st["p997"] >= 0.85:      # 이미 충분히 밝다 — 늘리지 않는다
    white = 1.0
# 무채색 후보에서 휘도 0.80 이상은 뺀다(전등갓은 흰색이 아니라 광원이다)
neutral = (lum > 0.12) & (lum < 0.80) & (s < 0.22)
```

- 전등갓은 `apply_look` 의 롤오프(무릎 0.82)로만 눌러 준다. 선형으로 늘려서 자르지 않는다.
- 할레이션(4-2)이 뜻이 있는 유일한 장면이 이것이다. 그래도 기본은 끔.
- 근본 처방은 촬영이다: 전등을 화면 밖으로 빼거나 얼굴 반대편 뒤쪽에 두고 밝기를 낮춘다([12](12_촬영_체크리스트.md)).

| 3 < 얼굴 ΔE ≤ 8 | 매칭을 돌린다(아래). 돌린 뒤에도 > 3 이면 경고 |
| 얼굴 ΔE > 8(매칭 전) | 매칭은 하되 리포트에 "원본 사이 조명이 크게 다름" |
| 벽(배경 중간톤) ΔE > 12 | 두 원본을 **한 장면 안에서 교차하지 않는다**([02](02_전체테이크_중복_처리_설계.md) 3-3 의 `alt_take_cutaways = False`). 이번 영상은 v2 기준 8.1~9.7 이라 통과하지만, 설치본 결과(12.4)로는 걸렸을 값이다 |

**방법**: 카메라마다 그레이드를 끝낸 뒤 얼굴 Lab 중앙값을 재고, 쓰인 길이로 가중한 평균을 기준으로 삼아 카메라마다 Lab 이동량을 구한다. 이동은 중간톤 가중이라 블랙·화이트는 그대로고, 픽셀 독립이라 같은 LUT 에 들어간다.

```python
def match_shift(x, d, k=0.8):                 # d = 기준 얼굴 − 이 카메라 얼굴 (dL, da, db)
    L, a, b = srgb_to_lab(x)
    w = 4 * (L / 100) * (1 - L / 100)         # 중간톤에서 1, 양 끝 0
    return lab_to_srgb(L + k * d[0] * w, a + k * d[1] * w, b + k * d[2] * w)

def match_sources(face_lab: dict[int, tuple], used_sec: dict[int, float]) -> dict[int, tuple]:
    ref = sum(np.array(face_lab[c]) * used_sec[c] for c in face_lab) / sum(used_sec.values())
    return {c: tuple(np.clip(ref - np.array(face_lab[c]), -6, 6)) for c in face_lab}   # 성분마다 ±6 상한
```

- 시제품 실측: 이동량 카메라 1 (−1.3, +1.1, +1.9), 카메라 2 (+1.3, −1.1, −1.9) → 얼굴 ΔE 5.0 → 1.8.
- `GradeChoice.match_lab` 에 저장하고 `grade()` 에서 `apply_look` 뒤 · `skin_guard` 앞에 건다.
- 비교 시트는 **모든 원본을 행으로** 넣는다(원본마다 1~2행). 컬러리스트는 한 번에 한 룩을 고르고, 판정 기준에 "행 사이 얼굴색이 같은가"가 들어간다.
- 벽 ΔL 이 크게 남는 것(조명 배치가 다름)은 LUT 로 못 고친다. 리포트에 적고, 촬영 체크리스트로 보낸다.

### 2-7. 색 태그 · 비트 심도 · 인코더

1. **`renderer/scripts/render.mjs`**: `renderMedia({... colorSpace: 'bt709' ...})`. 설치된 4.0.530 은 이 값일 때 태그 4개와 `zscale=matrix=709:range=limited:…` 변환을 붙인다(소스 확인, 렌더는 실행 검증 안 함).
2. **출력 단언**: export 뒤 `ffprobe` 로 `color_space == color_transfer == color_primaries == "bt709"`, `color_range == "tv"`, `pix_fmt == "yuv420p"` 를 확인한다. 아니면 게이트 F6 경고.
3. **LUT 는 16비트에서** — 실행 검증함:
   ```
   scale=in_color_matrix=<matrix>,format=gbrp16le,
   lut3d=file='grade_N.cube':interp=tetrahedral,
   zscale=m=bt709:r=tv:d=error_diffusion,format=yuv420p
   ```
   8비트 경로와 속도 차이가 없었다(4초 구간 1.9초 vs 2.0초). 이 소재에서는 밴딩 개선이 작았다(같은 값 이웃 비율 0.62 → 0.55). 잡음이 적은 미러리스·깨끗한 벽에서 효과가 난다. `gbrpf32le` 는 쓰지 않는다(같은 LUT 인데 평균이 달라졌다).
4. **NVENC 진단**: `_nvenc_variant()` 가 실패하면 stderr 첫 줄("minimum required Nvidia driver …")을 로그와 `진단.md` 에 적는다.
5. **썸네일 경로**(`pipeline.py` 의 `format=gbrp,lut3d`)도 3번과 같은 헬퍼를 쓴다.
6. **이미 만든 완성본 고치기**(다시 렌더하지 않을 때, 실행 검증 안 함): `-vf "scale=in_range=pc:in_color_matrix=bt601:out_range=tv:out_color_matrix=bt709,format=yuv420p" -c:v libx264 -crf 16 -preset slow -colorspace bt709 -color_primaries bt709 -color_trc bt709 -color_range tv`.
7. 2단 인코딩(메자닌 → `-tune film`, GOP = fps/2, B 프레임 2)은 P2. 근거는 리서치 10.3.

### 4-1. 얼굴 쪽 비네트(Remotion)

- `components/fx/Grain.tsx` 의 `Vignette`(화면 중심 50% 45%, 검정 알파 0.22)를 얼굴 중심 곱하기로 바꾼다.
- **매 프레임 바뀌는 스타일을 만들지 않는다.** 중심은 프레임마다가 아니라 **샷마다**(그 클립 구간 얼굴 트랙의 중앙값) 정한다. 그라데이션 문자열이 샷 안에서 고정이라 Chrome 이 다시 그릴 것이 없다. SVG 필터도 `backdrop-filter` 도 쓰지 않는다.
- 화자 판(둥근 판)·액자 샷 안에서는 세기 절반, 전면 그래픽이 덮는 동안은 그리지 않는다.

```tsx
export const FaceLight: React.FC<{x: number; y: number; s: number; k?: number}> = ({x, y, s, k = 1}) => {
  const e = Math.round(255 * (1 - 0.2 * k));
  return (<AbsoluteFill style={{pointerEvents: 'none'}}>
    <AbsoluteFill style={{mixBlendMode: 'multiply', background:
      `radial-gradient(${95 + s * 60}% ${115 + s * 60}% at ${x * 100}% ${y * 100}%, #fff 0 36%, rgb(${e},${e},${e}) 100%)`}} />
    <AbsoluteFill style={{mixBlendMode: 'soft-light', opacity: 0.08 * k, background:
      `radial-gradient(${s * 150}% ${s * 180}% at ${x * 100}% ${(y - 0.02) * 100}%, #fff 0, transparent 70%)`}} />
  </AbsoluteFill>);
};
```
실행 검증 안 함(렌더러를 돌리지 않았다). 8비트 그라데이션 밴딩을 막으려면 그 위로 입자가 지나가야 한다.

### 4-2. 할레이션 · 확산(FFmpeg, 프록시 단계) — 실행 검증함

`gbrp16le` 상태(2-7 의 3번 체인 안, `lut3d` 와 `zscale` 사이)에 넣는다. 1080p 기준 값이고, 다른 높이면 σ 를 높이에 비례시킨다.

```
# 할레이션: 문턱 0.72, 색 1.0 : 0.32 : 0.10, 세기 0.10
split[m][h];[h]scale=iw/4:ih/4:flags=bilinear,
  colorlevels=rimin=0.72:gimin=0.72:bimin=0.72:romax=0.10:gomax=0.032:bomax=0.010,
  gblur=sigma=1.7:steps=2,scale=iw*4:ih*4:flags=bilinear[halo];[m][halo]blend=all_mode=screen

# 확산: 문턱 0.45, 2탭(게인 0.07 · 0.05)
split=3[m][a][b];
[a]scale=iw/4:ih/4:flags=bilinear,colorlevels=rimin=0.45:gimin=0.45:bimin=0.45:romax=0.07:gomax=0.07:bomax=0.07,gblur=sigma=1.0:steps=2,scale=iw*4:ih*4:flags=bilinear[g1];
[b]scale=iw/8:ih/8:flags=bilinear,colorlevels=rimin=0.45:gimin=0.45:bimin=0.45:romax=0.05:gomax=0.05:bomax=0.05,gblur=sigma=2.0:steps=2,scale=iw*8:ih*8:flags=bilinear[g2];
[m][g1]blend=all_mode=screen[t];[t][g2]blend=all_mode=screen
```

- **`blend` 의 `all_opacity` 를 16비트에서 쓰지 않는다.** 처음 쓴 체인(`all_opacity=0.08`)은 암부가 뜨고(0.5% 지점 2 → 23) 보라·초록 얼룩이 생겼다. 세기는 `colorlevels` 출력 최댓값에 넣는다.
- 높이·폭이 8 의 배수가 아니면 `scale=iw*4` 로 원래 크기가 안 나온다. 코드는 프록시 크기를 알고 있으니 숫자로 적는다.
- 켜는 조건(제안): 확산은 얼굴 선명도가 영상 중앙값 이상이고 등급 0~1 일 때만. 할레이션은 `practical` 이고 휘도 0.75 이상 화소가 0.5~10% 일 때만(이번 2번 카메라: HEAD 기준 9.4%).
- 이번 소재에서 본 효과는 전등갓 가장자리의 옅은 번짐 정도다. **이것으로 영상이 달라지지는 않는다.** 순서를 P2 에 둔 이유다.

## 7. (f) 색 게이트 F

[`08_품질_게이트.md`](08_품질_게이트.md) 의 구조(`GateResult`, `block | repair | warn`)를 따른다. B8(클립아트)·B9(표면 종류)는 그대로 두고, 색은 F 로 더한다. F1~F5 는 프록시를 만든 직후(렌더 전), F6~F7 은 완성본에서 돈다. 문턱은 제안이다.

| id | 검사 | 재는 법 | 기준 | level | 수리 | 이번 영상 |
|---|---|---|---|---|---|---|
| F1 | 평평한 면의 얼룩 | 원본 프레임에서 기울기가 작은 영역(벽)을 찾고, 그레이드 전후 그 영역의 a\*·b\* 표준편차 비와 "색상이 영역 중앙값에서 12° 넘게 벗어난 화소 비율" | 비 ≤ 2.0 이고 벗어난 화소 ≤ 1% | block | `skin_guard` 를 끄고 다시 굽는다 → 그래도 실패면 룩 세기 0.5 | 설치본 ×4.36 · 2.1~14.7% **실패**, HEAD ×1.34 · 0% 통과 |
| F2 | 피부 범위 | 얼굴 상자 Lab 중앙값 | 색상 32~60°, 채도 ≤ 30(지금 상수), L\* 55~80 | repair | `skin_guard` 재적용, 노출 ±0.1 | 색상 42~46° 통과. 채도는 1번 28.2 통과, 2번 30.6 으로 상한을 조금 넘는다(경계) |
| F3 | 원본 사이 차이 | 2-6 | 얼굴 ΔE ≤ 3 · 배경 ΔE ≤ 12 | repair / warn | `match_sources` → 배경이 넘으면 교차 금지 | 설치본: 얼굴 4.7 · 배경 12.4 **실패** |
| F4 | 날아간 하이라이트 | 채널 최댓값 ≥ 0.985 화소 | 화면 ≤ 2% **이고** 원본 대비 증가 ≤ 1%p, 얼굴 상자 ≤ 0.5% | repair | 화이트 포인트 1.0 으로 다시 | 설치본 2번 4.41%(원본 0.19%) **실패** |

| F6 | 색 태그 | `assert_bt709` | 넷 다 일치 | warn("검토 필요") | 2-7 의 6번 변환 | **실패**(`pc` · `bt470bg`) |
| F7 | 자료의 톤 범위 | 전면·pip 자료 프레임의 블랙·화이트·채도 중앙값 | 블랙 ≥ 잉크의 50%, 화이트 ≤ 종이 + 2%, 채도 ≤ 화자 구간 × 1.5 | repair | [07b](07b_자료_하우스_트리트먼트.md) 처리 | 처리 없음 — 실패했을 값(스톡 화이트 1.0, 블랙 0.09) |

F1 구현 스케치:
```python
def blotch_index(before, after, box=None):
    """평평한 영역에서 색 잡음이 몇 배가 됐나. before/after: 같은 프레임의 원본·그레이드(0~1)."""
    flat = _flat_mask(before) if box is None else box       # 휘도 기울기 < 0.01, 면적 상위 연결 영역
    _, a0, b0 = srgb_to_lab(before[flat]); _, a1, b1 = srgb_to_lab(after[flat])
    h = _lab_hue(a1, b1); d = np.abs(_wrap(h - np.median(h)))
    return {"ratio": float(max(a1.std() / max(a0.std(), 0.2), b1.std() / max(b0.std(), 0.2))), "off": float((d > 12).mean())}
```
(고정 상자 버전은 실행 검증함 — 1-1 의 수치. `_flat_mask` 는 실행 검증 안 함.)
